# ПОС — Преподавательская оценка студентов

Консольное приложение на **Go** для управления оценками студентов по заданным критериям с учётом их весов.

Проект реализован с использованием принципов **ООП, SOLID, DDD и Hexagonal Architecture**. Для внедрения зависимостей используется **Uber Fx**, для проверки корректности — модульные тесты Go.

## 1. Возможности приложения

- Добавление и просмотр студентов.
- Создание критериев оценивания с максимальным баллом и весом.
- Автоматическое создание стандартного рубрикатора.
- Выставление, изменение и удаление оценок.
- Просмотр оценок конкретного студента.
- Расчёт итогового балла по взвешенным критериям.
- Экспорт итоговых результатов в CSV.
- Проверка корректности вводимых данных.

Итоговая оценка рассчитывается по формуле:

$$
S = 10 \cdot \sum_{i=1}^{n} \frac{s_i}{m_i} \cdot w_i
$$

где:

- \(s_i\) — полученный балл по критерию;
- \(m_i\) — максимальный балл;
- \(w_i\) — вес критерия;
- \(n\) — количество критериев.

Сумма весов должна равняться 1. Результат округляется до двух знаков после запятой.

**Пример:**

| Критерий | Балл | Вес |
|---|---|---|
| Домашние задания | 8/10 | 0.4 |
| Контрольная работа | 9/10 | 0.3 |
| Экзамен | 10/10 | 0.3 |

Итог: **8.90 из 10**.

## 4. Архитектура

Используется **Hexagonal Architecture (Ports & Adapters)** с выделением доменного и прикладного слоёв.

| Слой | Назначение |
|---|---|
| Domain | Сущности, Value Objects, бизнес-правила и расчёт итогов |
| Application | Сценарии приложения и интерфейсы зависимостей |
| Adapters | Консольный интерфейс, хранение в памяти и CSV-экспорт |
| Bootstrap | Создание и связывание зависимостей через Uber Fx |

Основная бизнес-логика не зависит от способа ввода данных и конкретного хранилища.

Такое разделение позволяет заменить консоль другим интерфейсом, а хранение в памяти — базой данных, не переписывая доменную логику.

## 5. Domain-Driven Design

При проектировании выделены следующие элементы DDD.

**Entities:**

- `Student` — студент с уникальным идентификатором.
- `Criterion` — критерий оценивания.
- `Evaluation` — оценка студента по критерию.

**Value Objects:**

- `Score` — балл с проверкой допустимого диапазона.
- `Weight` — вес критерия с проверкой значения.

**Aggregate Root:**

`Rubric` управляет набором критериев, контролирует уникальность их идентификаторов и сумму весов.

**Domain Service:**

`ScoreCalculator` рассчитывает итоговую оценку, используя заданную стратегию.

Основные бизнес-инварианты:

- ID и имя студента не могут быть пустыми.
- Максимальный балл критерия должен быть положительным.
- Вес критерия должен находиться в диапазоне (0; 1].
- Сумма весов не должна превышать 1.
- Для расчёта итога сумма весов должна равняться 1.
- Оценка не может быть отрицательной или превышать максимум критерия.
- Нельзя выставить оценку по отсутствующему критерию.
- Повторное выставление оценки запрещено; изменение выполняется отдельной операцией.

## 6. Принципы SOLID

### S — Single Responsibility Principle

Каждый компонент имеет свою ответственность.

- `Student` — данные и правила студента.
- `Rubric` — управление критериями.
- `ScoreCalculator` — расчёт итогового балла.
- `Service` — организация сценариев приложения.
- `Exporter` — экспорт результатов в CSV.

### O — Open/Closed Principle

Для алгоритма расчёта предусмотрен интерфейс `ScoreStrategy`.

Новый алгоритм можно реализовать отдельным типом, не изменяя сам `ScoreCalculator`.

### L — Liskov Substitution Principle

Реализации портов должны соблюдать их контракты.

Например, вместо `memory.StudentRepository` можно подключить другую реализацию `application.StudentRepository`, сохранив ожидаемое поведение операций сохранения и поиска.

### I — Interface Segregation Principle

Для разных задач выделены небольшие интерфейсы:

- `StudentRepository`
- `RubricRepository`
- `EvaluationRepository`
- `ResultExporter`
- `ScoreStrategy`

Компоненты не обязаны реализовывать методы, которые не относятся к их ответственности.

### D — Dependency Inversion Principle

Прикладной сервис зависит от интерфейсов репозиториев и экспортера, а не от их конкретных реализаций.

Реализации передаются через конструктор `NewService()`, а связывание компонентов выполняется в `bootstrap/container.go`.

## 7. Паттерны проектирования GoF

### Builder — порождающий

**Файл:** `domain/rubric_builder.go`

`RubricBuilder` позволяет пошагово собрать рубрикатор из нескольких критериев и проверить его перед использованием.

Применяется в `Service.CreateDefaultRubric()`.

### Strategy — поведенческий

**Файл:** `domain/calculator.go`

Интерфейс `ScoreStrategy` отделяет алгоритм вычисления итогового балла от `ScoreCalculator`.

Текущая реализация — `WeightedScoreStrategy`.

### Facade — структурный

**Файл:** `application/service.go`

`Service` предоставляет консоли единый набор прикладных операций, скрывая взаимодействие с репозиториями, доменными сущностями и калькулятором.

Благодаря этому консоль не обращается напрямую к хранилищам и не рассчитывает оценки самостоятельно.

## 8. Dependency Injection — Uber Fx

Для сборки зависимостей используется библиотека **`go.uber.org/fx`**.

**Файл:** `internal/bootstrap/container.go`

В контейнере регистрируются:

- репозитории студентов, критериев и оценок;
- CSV-экспортер;
- калькулятор;
- Application Service;
- консольный адаптер.

`fx.Provide()` регистрирует конструкторы, `fx.Invoke()` получает собранные зависимости, а запуск и завершение приложения управляются через `fx.App`.

DI-контейнер находится вне Domain и Application. Это позволяет тестировать бизнес-логику без запуска Uber Fx.

## 11. Ограничения и расширяемость

В текущей версии данные хранятся в оперативной памяти и не сохраняются между запусками.

CSV используется для экспорта итогов, а не для восстановления состояния приложения.

Возможные расширения:

- PostgreSQL вместо in-memory хранилища;
- JSON-экспорт;
- HTTP API вместо консольного интерфейса;
- дополнительные стратегии расчёта;
- поддержка нескольких независимых рубрикаторов.

Разделение на слои позволяет реализовывать эти расширения с локальными изменениями, сохраняя основную бизнес-логику там, где её правила не меняются.
